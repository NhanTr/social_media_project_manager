## Composer and durable drafts

Open composer from the feed. Camera and gallery actions use `image_picker`; recover Android lost picker data on startup. Copy picked bytes immediately into app-owned durable storage, scoped to the authenticated account. Support JPEG/PNG still photos; platform conversion to JPEG where supported; unsupported/corrupt formats produce a clear message.

Keep original bytes and editable crop/filter settings. Provide original ratio and adjustable square crop with preview, plus original, monochrome and warm filters. Apply orientation, crop and filters to the actual encoded upload, not only the preview. Perform expensive work outside the UI thread. Resize to a maximum edge of 2048px and encode JPEG below a 5 MiB client limit, safely below the backend 10 MiB image limit; fail clearly if preparation cannot satisfy the bound. Caption length is at most the API's 2000 characters.

Persist draft metadata after each user change, serialize writes, and persist the prepared file and immutable publish payload before any network operation. Draft contains account ID, stable client request UUID, source/prepared image references, caption/settings, upload session, finalized metadata and stage. Draft recovery must survive process termination; logout/account switch must never expose another account's draft. Clear completed drafts only after the successful post response is durably handled. Let users discard a draft explicitly.

Publish stages: editing → preparing → creating upload session → uploading → finalizing → creating post → published. Show real transmitted-byte progress for PUT and named progress for other stages. Disable duplicate submission. Cancellation aborts network upload and retains recoverable draft; never continue to create a post after cancellation. If create has already been sent, show an uncertain result and retry with the same immutable key/payload to reconcile it, rather than claim that a server-side post was undone.

Reuse completed stages on retry. Expired uploads can restart safely. A new edited publication gets a new request key; an ambiguous in-flight publication must be reconciled before mutating its immutable payload. On success navigate back to feed, refresh it and acknowledge publication. Since the normal feed contains friends' posts, use the returned own-post detail/confirmation instead of injecting an own post into friends-only results.

## Backend reliability boundary

Add an optional `clientRequestId` UUID to create-post requests for compatibility. Deduplicate by authenticated user and UUID using a database uniqueness constraint and transaction-safe serialization or atomic insertion. Store a request fingerprint; identical retries return the same post, differing payloads with the same key return a stable conflict. Concurrent retries must create exactly one post and one notification fan-out. Preserve existing deleted/hidden state when replaying; never recreate deleted content.

Associate new mobile publications with a finalized upload owned by the caller. Verify the upload's final metadata and avoid trusting arbitrary client metadata for this new path. Make finalize replay safe for its owner, retaining/reconstructing the same validated metadata. A cancelled or abandoned upload must remain eligible for cleanup; consumed media must not be deleted by the orphan cleanup job.

Keep changes in post-service and new Flyway migrations. Preserve existing API paths and public/internal authentication. Update API catalog, business flow and roadmap documents together with contract changes. No broad service refactoring.

## Feed, detail and save

Feed controller owns items, current friend ID, opaque cursor, loading/error/offline states and a request generation number. Refresh replaces results and resets pagination; load-more appends by unique post ID. Deduplicate overlapping requests and ignore responses from an earlier filter/refresh. A successful empty refresh clears old visible/cache items. Forbidden friend content clears that filter's content rather than showing cached posts as current.

Use the friends list to choose one friend or all friends. Preserve per-account/per-filter first-page snapshots and last-success time. Cache only bounded first-page metadata and available thumbnail/image bytes in app-private storage. Offline fallback shows a visible stale/offline indicator; do not treat network failure as empty success. Cache never overrides an authoritative 403/404 or successful refresh. Clear/invalidate account and blocked-user snapshots on relevant session/social events.

Media detail rechecks `GET /api/v1/posts/{id}`. A 403/404 displays unavailable content and removes the corresponding item/cache entry. Allow zoom. Save only after a fresh authorization check; download with bounded size/timeout and save via `gal` with add-only Photos permission where supported. Handle denied/restricted/limited access and insufficient space with useful Vietnamese messages. Do not download or save previously cached media after access has been denied.
